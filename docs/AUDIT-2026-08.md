# EngiSync — System Audit

**Date:** 9 August 2026 · **Scope:** whole system · **Method:** source inspection, production probing, production database queries.

Every finding below cites the file or the measurement it came from. Where I could not verify something, it says so. Nothing here is inferred from how the code "probably" behaves.

---

## 0. Executive summary

EngiSync is in better structural shape than its age suggests: 56 models with 70 indexes, 202 passing tests, a real CSP, bcrypt at cost 12, TOTP 2FA, atomic distributed rate limiting, and an authorisation layer (`ProjectGrant`) that was rebuilt this month to be capability-based rather than role-guessed.

It also has **three defects that make it unsafe to grow**, and one of them is live right now.

| # | Finding | Severity |
|---|---|---|
| C1 | Email is unconfigured in production — password reset and email verification are both dead for all 41 users | **Critical** |
| C2 | 2FA has no backup codes; combined with C1, enabling 2FA can permanently destroy an account | **Critical** |
| C3 | File bytes are stored inside Postgres; this does not survive growth | **Critical (latent)** |
| H1 | OAuth account linking is enabled on unverified emails — pre-registration account takeover | **High** |
| H2 | JWT sessions cannot be revoked; password reset does not log other devices out | **High** |
| H3 | No security event log, no login alerts, no device list, no account activity history | **High** |
| M1 | Notifications: 4 types, 3 trigger sites, no email, no preferences, no digest | **Medium** |
| M2 | `emailVerified` is collected but gates nothing | **Medium** |

The user's stated priority — "a user who loses access can become permanently locked out" — is correct, and is worse than described. It is not one flaw, it is **C1 + C2 + H2 acting together.**

## 1. Authentication & account recovery

### C1 — Production cannot send email · **Critical** · *live now*

**Existing problem.** `/forgot` returns "Email isn't configured on this server, so reset links can't be sent yet." Verified by submitting a non-existent address against production on 9 Aug 2026, which returns before any send occurs.

**Root cause.** `isEmailConfigured()` (`src/lib/email.ts:19`) requires either `RESEND_API_KEY` or the `SMTP_*` set. The local `.env` has `SMTP_HOST`, `SMTP_USER`, `SMTP_PASS`, `EMAIL_FROM`. **Vercel production has none of them.** This is a deployment gap, not a code defect — the code fails honestly rather than pretending a link was sent, which is to its credit.

**Blast radius, measured.** 41 users total; **38 have `emailVerified: null`**. Email has almost certainly never worked in production. Every one of those 41 people is one forgotten password away from needing manual database intervention.

**Risk level.** Critical. Not theoretical — it has already happened once (`2004reecejames2605@gmail.com`, resolved by hand-issuing a token).

**Recommended solution.** Set `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `EMAIL_FROM` in Vercel → Settings → Environment Variables (Production), redeploy, then verify delivery end-to-end.

**Better alternative.** Move to Resend with a domain you control. `EMAIL_FROM` currently defaults to `EngiSync <onboarding@resend.dev>` (`src/lib/email.ts:31`) — a shared sender domain that Gmail treats poorly. Auth email that lands in spam is the same as no auth email. **Add SPF and DKIM.** This matters more than any code change in this report.

**Impact on users.** Self-service recovery starts working for everyone. No UI change; the capability simply stops being broken.

### C2 — 2FA with no recovery path · **Critical**

**Existing problem.** `User` has `twoFactorEnabled` and `twoFactorSecret` and **nothing else** (`prisma/schema.prisma`). There are no backup codes, no recovery codes, no admin-assisted reset flow.

**Root cause.** 2FA was implemented as an authentication check (`src/auth.ts` — `verifyTotp` in `authorize`) without the recovery half of the feature. This is the single most common way 2FA ships incomplete.

**Risk level.** Critical, and *self-inflicted by the most security-conscious users*. A student who loses or wipes their phone is locked out permanently: `authorize()` returns `null` with no alternative path, and while C1 stands there is not even an email route around it.

**Recommended solution.**
1. `TwoFactorBackupCode { id, userId, codeHash, usedAt }` — ten single-use codes, **bcrypt-hashed** exactly like passwords, shown once at enrolment.
2. Accept a backup code wherever a TOTP code is accepted.
3. Warn at 3 remaining; offer regeneration (which invalidates all previous).
4. **Refuse to enable 2FA until the codes are downloaded or copied.** Enrolment without stored recovery is the failure mode itself.

**Better alternative.** WebAuthn/passkeys as a second factor and eventually a first factor — phishing-resistant and, on a modern Android phone, a fingerprint instead of a code. Recommend as a later phase; backup codes are the correct immediate fix because they are simple and dependency-free.

**Impact on users.** 2FA becomes safe to recommend. Today it should honestly carry a warning.

### H1 — Pre-registration account takeover via OAuth linking · **High**

**Existing problem.** Both providers set `allowDangerousEmailAccountLinking: true` (`src/auth.ts`). Registration does not require a verified email.

**Root cause.** The flag silently links any OAuth identity to an existing account with a matching address. Auth.js names it "dangerous" for a reason.

**The attack.** An attacker registers `victim@university.ac.zw` with a password they choose. Nothing verifies they own it (C1 guarantees this). The real owner later signs in with Google, and Auth.js links their Google identity **into the attacker's account**. Both parties now have access; the attacker keeps password access indefinitely and sees everything the victim does.

**Risk level.** High. Trivially executable, requires only knowing a classmate's university address, and leaves no trace in any log.

**Recommended solution.** Either (a) link only when the existing account already has `emailVerified` set, or (b) require verification before an account can hold any project data. Option (b) is stronger and depends on C1.

**Better alternative.** Restrict OAuth to the institutional tenant (Microsoft Entra with a fixed `issuer`) so identity is asserted by the university, not by a self-service Google account.

**Impact on users.** Legitimate users notice nothing. The current convenience is only convenient because it is unsafe.

### H2 — Sessions cannot be revoked · **High**

**Existing problem.** `session.strategy = "jwt"`, `maxAge` 30 days (`src/auth.config.ts:14-16`). A JWT is valid until it expires; the server holds no state to invalidate.

Concretely: `resetPassword()` (`src/app/(auth)/forgot/actions.ts`) rewrites the hash and burns the tokens — **but every already-authenticated device stays signed in for up to 30 days.** If the reset was triggered *because* the account was compromised, the reset does not evict the attacker. That inverts the entire point of a password reset.

**Root cause.** JWT sessions were chosen for edge-middleware performance. The trade-off is real, but nothing was added to compensate.

**Recommended solution.** Add `sessionVersion Int @default(0)` to `User`. Embed it in the JWT; reject any token whose version is stale. Increment on password reset, 2FA change, and explicit "sign out everywhere". This preserves stateless verification for the common path and costs one integer comparison.

**Better alternative.** Database sessions give real revocation and a device list for free, at the cost of a query per request and the loss of edge middleware. **Recommend the `sessionVersion` approach** — it buys the security property without surrendering the architecture.

**Impact on users.** A "sign out of all devices" control that actually works, and password reset that genuinely ends a break-in.

### H3 — No security events, no activity history · **High**

**Existing problem.** `AuditLog` covers 31 product actions (evidence, workspaces, grants, AI runs) and **almost no authentication events**. There is `PASSWORD_RESET` and `USER_REGISTERED`; there is no `LOGIN_SUCCEEDED`, `LOGIN_FAILED`, `PASSWORD_CHANGED`, `TWO_FACTOR_ENABLED`, `TWO_FACTOR_DISABLED`, or `EMAIL_CHANGED`.

**Consequence.** A student cannot answer "has someone else been in my account?", and neither can you. There is no login alert, no device list, and no way to detect a slow credential-stuffing campaign, because failures are counted for throttling and then discarded.

**Related gap — throttling is IP-only.** `login:${clientIp}` at 10 per 5 minutes (`src/app/(auth)/login/actions.ts:24`). Sound as far as it goes, but there is **no per-account limit**, so an attacker spread across many IPs can grind one account indefinitely. Conversely a whole campus behind one NAT shares a single bucket — the limit is simultaneously too weak for the attacker and too harsh for the class.

**Recommended solution.** Log auth events with IP and user-agent; add a per-account limiter alongside the per-IP one; email on new-device sign-in and on every security-sensitive change; surface the last 20 events in Settings.

**Better alternative.** Send the *notification* even when suppressing the *log noise* — an alert the user reads beats a log nobody opens.

**Impact on users.** Recovery stops depending on you, because users can see and act on their own account activity.

### What is already correct (do not "fix" these)

Verified sound; called out so nobody regresses them under time pressure:

- **Reset tokens** — 32 random bytes, base64url, 1-hour expiry, single-use, and **all sibling tokens invalidated in the same transaction** (`forgot/actions.ts`). This is textbook.
- **Enumeration resistance** — `/forgot` returns an identical message whether or not the account exists.
- **Password hashing** — bcrypt cost 12, both at registration and reset.
- **CSRF** — Server Actions carry Next's built-in origin checks; no product REST surface exists to forget.
- **SQL injection** — Prisma parameterises everywhere; no raw SQL outside the rate-limit upsert, which is parameterised.
- **XSS** — React escapes by default; a CSP is set with `X-Frame-Options: DENY` and HSTS (`next.config`).
- **SSRF** — `externalUrl` evidence is stored and rendered, never fetched server-side. The schema comment says so explicitly, and the code matches.
- **Upload limits** — `MAX_FILE_BYTES` enforced before any read, plus a 10 MB Server Action body cap.

## 2. Reliability & scalability

### C3 — Files live in Postgres · **Critical (latent)**

**Existing problem.** `FileResource.data Bytes?` — uploads are stored as bytes **inside the database**.

**Root cause.** Expedient at 41 users, and it made the evidence model easy to build. It does not survive the stated goal of hundreds of thousands.

**Why it fails, specifically.** Every download materialises the whole file in server memory before sending; concurrent downloads multiply that. Postgres backup and restore time scales with total upload volume, so recovery time degrades as the product succeeds. Neon storage is billed and sized for rows, not blobs. Every `SELECT` that forgets to exclude `data` drags megabytes through the connection.

**Risk level.** Critical but latent — nothing breaks today, and it will break suddenly rather than gradually.

**Recommended solution.** Move bytes to object storage (Vercel Blob or S3); keep the metadata row and store a key. Migrate lazily: write new uploads to blob, backfill in the background, read from whichever is populated. The `data` column is already nullable and `externalUrl` already models "the bytes are elsewhere" — **the schema is over half way there.**

**Impact on users.** Faster downloads, no visible change otherwise.

## 3. Notification ecosystem

> **CORRECTION (9 Aug, during Phase 3).** The two sentences originally here
> were wrong, and wrong in the direction that flatters the audit. I wrote that
> there was "no dispatcher", "no email delivery" and "no scheduling". In fact
> `lib/notifications.ts` already provides a single `createNotification()` with
> dedupe, email and web-push delivery, and `/api/cron/reminders` already runs
> daily on Vercel Cron with `CRON_SECRET` auth. I counted `notification.create`
> call sites and inferred an absence instead of reading the module. The
> corrected finding is below.

**Existing problem.** The request lists 23 notification categories. Reality:
**4 enum values** (`TASK_DUE`, `WORKSPACE`, `MENTION`, `SYSTEM`) and two global
email switches. What is genuinely missing is *control and restraint*, not
plumbing: no per-category preferences, no quiet hours, no batching or digest,
no notion of priority — every notification is delivered immediately and
identically.

There is also a live defect: `generateDueSoonNotifications` is called from the
**navbar on every page render**, throttled by an in-memory `Map`. On serverless
each instance holds its own map, so the throttle barely throttles, and every
navigation pays for a task scan that the daily cron has already done.

**Root cause.** Notifications grew feature by feature — a bell, then email,
then a cron — without anyone deciding what a user should be able to turn off.

**What the schema gets right.** `dedupeKey` with `@@unique([userId, dedupeKey])` — deduplication was designed in from the start, which is the hard part and usually the part retrofitted in pain.

**Recommended architecture.**
1. **One dispatcher.** `notify({ userId, type, title, body, link, dedupeKey, priority })` as the single entry point; no feature writes `notification.create` directly. Today's 3 sites become N without N copies of the delivery rules.
2. **Preferences per type per channel** — a `NotificationPreference` row, defaulting to sensible on/off rather than everything on.
3. **Priority decides the channel.** Urgent (supervisor feedback, deadline today) → in-app + email immediately. Routine (task completed by a teammate) → in-app, and roll up into a digest.
4. **Quiet hours + digest** need scheduled execution. Vercel Cron, one job hourly, batching anything not yet delivered.
5. **Push is already half-built** — `PushSubscription` exists and `sw.js` handles `push`. It needs the dispatcher, not new plumbing.

**Better alternative than what was asked for.** The brief says "users should never miss important project events". The higher-leverage version is **deadline-derived reminders computed from task and milestone dates**, rather than more event types. One well-timed "your interim report is due in 3 days and section 4 has no evidence" is worth twenty task-completion pings. Notification *volume* is what makes students disable notifications.

**Risk level.** Medium. Nothing is broken; the capability is thin.

## 4. Simplicity & UX

Deferred to a dedicated pass, with one exception worth stating now.

**M2 — `emailVerified` gates almost nothing.** *(Partly corrected 9 Aug: `verifiedAccountGate` already existed and was applied to project and department creation. The finding as written overstated the gap.)*

**Status: addressed in Phase 5.** The gate now also covers invitations, share links, portfolio publishing, and the two money actions that ask other people to pay — the set whose consequences reach outside the account.

It is **deliberately dormant while C1 stands**: `verifiedAccountGate` returns null when SMTP is unconfigured, so nobody is asked for a verification they have no way to obtain. Enforcement switches itself on the moment email works. Ordinary coursework — uploading evidence, declaring a payment already made — is deliberately NOT gated, because blocking that punishes a student for an operator's misconfiguration.

## 5. Project idea library — scope challenge

The brief asks for **1,000 ideas across 20 departments with 15 structured fields each.** I want to be straight about what that is: roughly **15,000 pieces of content**, and it is a content and quality problem, not an engineering one. The engineering — a `ProjectIdea` model, department scoping, faceted filters — is perhaps two days. Generating 1,000 genuinely *good*, non-duplicative, correctly-budgeted ideas is the other 95% of the work.

**My recommendation: do not build 1,000 up front.** Build the schema and the browse experience, seed **100 excellent ideas** across the departments you actually have users in, and add an "AI-assisted idea generation" path scoped to the student's department. Reasons:

- You have 41 users. A thousand ideas nobody has filtered is worse than a hundred that are all good — **choice paralysis is the failure mode**, not lack of options.
- Budgets, hardware availability, and supplier realities are **local**. An idea list written without Zimbabwean component availability and pricing in mind will quietly mislead students, and a wrong budget is worse than no budget.
- Ideas that come with a supervisor who will actually take them are worth ten that do not. `supervisor suitability` cannot be generated — it depends on your real staff.

If you still want the full thousand after that, the mechanism is the same and it becomes a batch content job, not a blocker.

## 6. Prioritised roadmap

**Phase 0 — Unblock recovery (hours, mostly yours)**
- Set SMTP env vars in Vercel; verify delivery end-to-end. *(C1)*
- Move `EMAIL_FROM` to a domain you control; add SPF/DKIM.

**Phase 1 — Make lockout impossible (Critical)**
- 2FA backup codes, hashed, mandatory acknowledgement at enrolment. *(C2)*
- `sessionVersion` revocation; reset and 2FA changes invalidate other sessions. *(H2)*
- Restrict OAuth linking to verified accounts. *(H1)*

**Phase 2 — Make compromise visible (High)**
- Auth event logging; per-account rate limiting; new-device email alerts; account activity in Settings. *(H3)*

**Phase 3 — Notifications as a subsystem (Medium)**
- Central dispatcher, preferences, priority routing, digest via cron, deadline-derived reminders. *(M1)*

**Phase 4 — Storage before it hurts (Critical-latent)**
- Blob storage with lazy migration. *(C3)*

**Phase 5 — Verification enforcement, then UX and the idea library**
- Gate sensitive actions on `emailVerified` *(M2)* — only after Phase 0 has been live long enough for users to verify.

**Sequencing rationale.** Phase 0 gates Phases 1, 2 and 5 — every one of them assumes email works. Phase 4 is Critical but latent and can therefore wait behind things that are Critical *and live*.

## 7. Testing strategy

Current: 202 tests, all passing, concentrated in `src/lib`. The gap is that **every finding above lives in code with no test**.

- **Security-property tests** — a reset token is single-use; siblings are invalidated; `/forgot` responses are byte-identical for existing and non-existing accounts; a stale `sessionVersion` is rejected; a used backup code cannot be replayed.
- **Regression pins** — one test per fixed finding, named for it, as `identity.test.ts` already does for the PII leak.
- **The `new Notification()` class of bug is invisible to all of this.** Chromium on desktop cannot reproduce an Android-only illegal constructor. That needs either a real-device pass or capability-shape assertions, and it is worth accepting that some mobile faults will only be caught in production — which is an argument for the error boundary reporting real diagnostics, now shipped.
